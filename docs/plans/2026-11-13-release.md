# `ws release` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `ws release` builds the code branch of every company repo of a release (the task branch
itself, or `release/YYYYMMDD` with the task branches merged in an explicit order), checks it,
publishes the push and the two PRs behind one approval, moves the release to another date, and
prints the PR links for the GMUD; the `/release` skill drives it.

**Architecture:** A package `ws.release` with one module per concern: config and texts, the release
folder and PR drafts, git operations, the `gh` adapter, the Alembic chain, the state of a repo and
its rules, and one module per command. The two writing commands build a `WritePlan` (every call
with its arguments and texts), hash it into the 12-hex approval code, and run it only from a
separate shell call with `--approve CODE`, behind today's approval gate, the same way as
`ws card apply`. Local commands (`branches`, `new`, `status`) never write to GitHub.

**Tech Stack:** Python 3.12+, standard library only at runtime; `git` 2.38+ (`merge-tree
--write-tree`), the `gh` CLI; `uv`, `pytest`, `ruff`.

**Spec:** `docs/specs/2026-10-27-release-design.md` (all of it; "Decisions (user, 2026-10-27)"
replace the earlier proposals and bind this plan).

## Global Constraints

- Runtime code: standard library only. Run everything with `uv run` (`uv run pytest -q`,
  `uv run ruff check`, `uv run ruff format --check`).
- Names in English (modules, flags, JSON keys, stderr messages). Text for people is PT-BR: PR
  titles and bodies, `gh` comments, merge subjects, the preview summary lines and the gate box.
- Output: JSON on stdout, messages on stderr. Exit codes: 0 ok, 1 a rule failed, 2 a precondition
  is missing (no `gh`, no config, no gate settings, a merge in progress), 3 a merge conflict that
  needs the user.
- Dates in: `YYYYMMDD` or `YYYY-MM-DD`; texts: `DD/MM/YYYY`; branches and folders: `YYYYMMDD`.
- Every command first runs `gitops.fetch` in each repo of the release (a failure is a warning in
  the JSON, never a stop); every command takes `--project SLUG`.
- R1 in code: no `gh pr merge`, no push to `base_branch` or `sandbox_branch`, no `-f`/`--force*`
  or `+` refspec, anywhere in `src/ws/release/`. GitHub is written only by `ws release publish` and
  `ws release move` with `--approve`, through `gh` and `git push`; never through the GitHub MCP.
- Merge commits the tool makes match `^(feat|chore|refact|fix|test)\(TS-\d+(, TS-\d+)*\): .+`, have
  at most 72 characters, are PT-BR, and never carry `Co-Authored-By`.
- Approval: code = first 12 hex of the SHA-256 of the plan; pending record mode 600, valid 30
  minutes, refused in the preview's shell session (`os.getsid(0)`); deleted before the first send.
- Config: `[release]` in `~/.config/workspace/config.toml`; working files and worktrees in
  `~/.local/share/workspace/projects/<slug>/release-YYYYMMDD/`. `<org>` is never written in this
  repo: fixtures use `acme/repo-a`, `acme/repo-b`, keys `TS-101`…, site
  `https://example.atlassian.net`.
- `ws` never edits `~/.claude/settings.json` or `config.toml`; it prints what to add.
- Commits of this repo: `feat:`, `fix:`, `test:`, `docs:` or `chore:`, PT-BR, at most 72
  characters, no task ID, no `Co-Authored-By`. `git diff` before each message.

## Rulings (where the spec predates today's code, or is silent)

1. **Gate:** today's `hooks/approval_gate.py` with a `ws release publish|move` family in
   `hooks/gate/bash_rules.py`, not a new `hooks/ask_release_write.py`, and built now on phase 1
   although `docs/backlog.md` says "waits for phase 2b" — the card hook became the single gate on
   2026-10-28 (`ask_card_apply.py` is only a shim), and decision 5 binds the `/card` approval; when
   phase 2 lands, card and release move together.
2. **Pending store** `~/.local/share/workspace/release/pending/<code>.json`, not under
   `release-DATE/` — the gate box must find the record by the code alone, as with
   `cards/pending/`; a move has two dates and `--project` may be absent.
3. **Branch presence on `origin`** is read from the remote-tracking refs after the
   `git fetch --prune` every command makes, not from `gh api repos/<slug>/branches/X` — same
   answer, one `gh` dependency less, and the fake `gh` keeps no branch table.
4. **Merge order and migrations:** the order is the `[include]` list (spec), plus two rules the spec
   lacks. R10: in a repo with `alembic` set, every migration an include adds names a
   `down_revision` that `origin/master` or an earlier include has, and the code tip and the sandbox
   side each have one Alembic head. R11: no include contains a later include, and no include
   carries commits of a key outside the list; local branches are not behind `origin`. `branches`
   prints `suggested_order` — the next release has six stacked branches with chained migrations:
   out of order, everything lands under one merge and one key, and `alembic upgrade head` fails on
   two heads.
5. **Long key lists:** a release-level merge subject keeps every key when the scope plus one word
   of the text fits 72; otherwise it keeps the leading keys that fit and the body lists them all
   (`Tarefas: …`). "Cut on a word" also cuts at `-` and `/` inside a branch name — past six keys the
   scope alone exceeds 72, and a branch name is one word.
6. **Past dates:** only `new DATE` and the NEW of `move` are refused in the past; OLD may be past —
   a release missed on its date is the usual reason to move it.
7. **Single-branch master merge** happens where the task branch is checked out (clean), else in a
   worktree `release-DATE/<repo>` on the task branch itself — git cannot merge into a branch that
   is not checked out.
8. **Sandbox head:** `<code branch>-sdbx` only while it exists and `origin/sandbox` still conflicts
   with the code branch; otherwise the code branch — task `-sdbx` copies exist by convention and
   must not take over the sandbox PR (decision 1).
9. **R5 scope:** first-parent merges of a `release/` branch and every commit of `code..sdbx`; in a
   single-branch repo only the merges `new` makes — task branches carry the user's own merges.
10. **`move` is also local:** the folder becomes `release-NEW/` and the drafts get the same date
    replacement as the PRs — so a later `publish NEW` (a second sandbox PR) passes R6.
11. **Items:** `branches --from-items SLUG` adds the cards of that project's items and uses their
    `blocks`/`blocked_by` as order hints — items now carry `card`.

## Review Focus

1. Includes listed out of stacked order (a later include already contains an earlier one, as each
   branch of the next release contains the one before it): `new` merges nothing in that repo, exits
   1 and prints `suggested_order` (Task 10).
2. Two includes that each add a migration on the same `master` head, or an `origin/sandbox` with a
   migration `master` lacks: `ready: false` naming both revisions and the side (Task 10).
3. A local task branch behind its `origin` copy (not pulled): never merged; the problem names it
   (Task 10).
4. A repo with six or more keys: the release-level merge subject still has at most 72 characters
   and matches R5 (Task 1).
5. Moving a release whose date already passed: allowed; only a past NEW is refused (Task 14).

## Parallel waves

Each wave runs its tasks in parallel worktrees (at most five agents); the orchestrator merges the
wave and runs `uv run pytest -q` before the next. No two tasks of a wave touch the same file, test
files included.

**Wave 0** (orchestrator, one commit `chore: pacote ws.release`): `src/ws/release/__init__.py`,
exactly:

```python
"""`ws release`: build, publish, move and report the release of the company repos."""

import json
import sys
from collections.abc import Callable

EXIT_RULE, EXIT_SETUP, EXIT_CONFLICT = 1, 2, 3


class ReleaseSetup(Exception):
    """A precondition is missing (config, gh, gate settings, a merge in progress): exit 2."""


class ReleaseRefused(Exception):
    """A rule failed and nothing was written: exit 1. `payload` is printed as JSON when given."""

    def __init__(self, message: str, payload: dict | None = None):
        super().__init__(message)
        self.payload = payload


def run(name: str, action: Callable[[], tuple[dict, int]]) -> int:
    try:
        payload, code = action()
    except ReleaseSetup as error:
        print(f"ws release {name}: {error}", file=sys.stderr)
        return EXIT_SETUP
    except ReleaseRefused as error:
        if error.payload is not None:
            print(json.dumps(error.payload, ensure_ascii=False, indent=2))
        print(f"ws release {name}: {error}", file=sys.stderr)
        return EXIT_RULE
    print(json.dumps(payload, ensure_ascii=False, indent=2))
    return code
```
